# Clinic messaging frontend

Open **Messages** in the clinic workspace. Access uses the exact tenant-local `messaging.internal.send`, `messaging.internal.receive`, and `messaging.patient.send` grants returned by `/api/user`. Legacy `messages.view`, role defaults and CRUD wildcards do not grant messaging access. Admin and patient roles never get patient messaging or consent review, even with explicit grants.

The inbox searches authorized subjects through `/api/conversation-threads`. It paginates 25 threads at a time. Type and read filters apply to the current page and are labeled accordingly. Read/unread state means opened/not opened **in this mounted session**; it is held in memory, cleared with the workspace/session, and uses a returned last-message ID or thread timestamp when available. The documented API has no read-state mutation, cross-device unread count or patient receipt endpoint. Durable unread state requires backend support.

New internal conversations select eligible staff from the existing `/api/users` directory. Exact receive grants are read from effective user permissions when supplied, otherwise from returned role permission catalogs. Admin recipients are excluded; the server remains authoritative for user overrides and direction checks. If the directory is forbidden or does not expose eligibility, the form does not accept arbitrary user IDs. Staff cannot reply to threads whose returned participant roles include an admin; backend authorization also rejects this direction. No participant management or legacy `/api/messages` operation is used.

Patient conversation creation uses the existing authorized patient selector and only the documented `care` / `billing` creation purposes. The opened thread fixes the patient ID and displays its identity, purpose, channel and participants above the history/composer. Patient identities from thread participants must agree. A confirmation must match the fixed patient ID, use case and exact body before it can be shown. There is no send action in list views.

Staff with the exact `messaging.preferences.manage` grant can see the current ledger decision for the thread's exact purpose/scope/in-app tuple. Missing, denied, withdrawn, revoked, malformed or failed decisions block the composer. Preparation also loads a fresh decision. Staff who only have patient send permission are told that ledger details are unavailable to their role; the frontend does not call the protected consent-review endpoint or invent a grant. Their sends still require explicit destination/message confirmation and consent acknowledgement, and the server enforces current patient consent at send time. Showing the actual consent status to these senders would require a separately authorized backend disclosure, such as including it in the confirmation response.

Preparing a token never sets send acknowledgement flags. The separate accessible review dialog shows recipient, in-app channel, purpose, consent state/visibility, full message and expiry. Both confirmation checkboxes start unchecked on every review. Expired confirmation cannot send. Flags are included only after the final explicit action. No consent evidence is created or changed by this workflow.

Transport failures retain the exact payload and idempotency key, lock editing and expose an explicit retry. Patient retries require a new review; no mutation retries automatically. Definitive authorization/validation denials preserve the draft and permit correction. An accepted operation clears the draft and refreshes history. `available` is clinic availability; `awaiting_portal` is recorded for future portal access, never delivered/read. There is no provider resend endpoint here, so failed provider delivery is not simulated as a new message. History renders sender, local timestamp, message ID, state and linked correction/redaction metadata as plain text. No attachment, correction or redaction authoring UI is added.

Sender names resolve from the tenant-authorized `/api/users` directory by each participant's `user_id`; message `sender_id` is a participant ID and `actor_id` is a user ID. History, recipients and participant labels share these resolved identities. The viewer's identity never replaces another participant's identity. If the directory is unavailable or an identity has been removed, stored participant identity/ID remains the fallback. Original message attribution is never rewritten.

Before each send, the frontend checks `/api/user` against the composing account and clinic. A mismatch blocks the POST and offers a session reload. This helps catch a changed login in another tab; the backend still authenticates the actual send request. Browser tabs in one profile share authentication cookies. Use separate browser profiles or a normal window and a private window to test two staff accounts concurrently.

## Backend setup and resource contract

The messenger uses the shared `UserAvatar` component also used by the account header: circular clinic-blue initials from the first two name parts, or a profile photo when supplied. The adapter accepts `profile_photo_url`, `avatar_url`, `profile_picture_url`, and `photo_url`; failed images fall back to initials. Directory photos stay attached to their actual sender identity. No profile upload endpoint is introduced.

Messages display as incoming/outgoing bubbles with sender avatars, day dividers, local times, and delivery state. Message IDs and full timestamps remain under each message's Details disclosure. Patient recipient/channel context, consent state, and final confirmation stay visible in the thread workflow.

This checkout contains the Next.js frontend only; there is no Artisan application to migrate or seed. Run the supplied messaging/consent migrations and PermissionSeeder in the backend deployment. Validate deployed resource names before rollout: the supplied endpoint brief specifies envelopes but does not provide complete JSON resources.

The adapter expects `data.threads`, `data.thread`, `data.messages`, `data.message`, `data.consent` and pagination under `meta.pagination` (camelCase or Laravel pagination keys). Confirmations use direct `data.confirmation_token`, `expires_at`, `patient_id`, `use_case`, and `body`. The adapter normalizes confirmation `patient_id` into the review identity and also accepts a matching nested `patient.id`; conflicting or absent IDs are rejected. Internal threads use `use_case=internal` with no patient identity. Threads expose numeric `id`, `subject`, optional `patient_id`, `use_case`, and detail `participants`. Participants expose numeric `id`, `user_id`/`patient_id`, optional `name`, and nested `user`/`patient` identity. Nested `user.roles[].slug` enables proactive staff-to-admin reply blocking. Messages expose `id`, `body`, `sender_id` (conversation participant ID), `actor_id` (authenticated user ID), `created_at`, `delivery_state`, and optional `kind`, `supersedes_id`, `reason`, `redacted`. Current consent exposes `patient_id`, `purpose`, `scope`, `channel`, `allowed`, `reason`, optional status/ledger/policy version. Mismatched identities/decisions fail closed. The existing API client supplies Sanctum credentials and the server-selected clinic header.

## Validation

- `npm run test:communications` covers exact messaging grants, role prohibitions, purpose/channel mapping, mismatched context, consent denial and confirmation/idempotency request contracts.
- `npm run test:messaging:browser` runs intercepted fixtures against a local server (default port 3016, configurable with `MESSAGING_TEST_URL` and `MESSAGING_TEST_API_URL`). It covers explicit review, cancellation, withdrawal after review, identity mismatch, retry key preservation, admin restrictions, subject search, internal sends and mobile layout. It never sends to a real clinic backend.
- `npm run build` verifies the production frontend.
